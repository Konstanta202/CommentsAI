# SM Analytics (CommentsAI) — статус проекта

> Составлено на основе анализа кода в репозитории на 2026-09-16. Общая готовность проекта (сквозной работающий пайплайн от сбора комментариев до дашборда): **≈25–30%**. Отдельные сервисы готовы на 40–70% как изолированные модули, но между ними отсутствуют критичные связующие звенья (см. «Что не работает»).

## Что это за проект

Система мониторинга и анализа комментариев из ВКонтакте: парсер собирает посты/комментарии из групп VK, ML-модель размечает их тегами/тональностью, а веб-часть (Gateway + User Service + Analytics) должна предоставлять API и дашборд для просмотра результатов в реальном времени.

Задуманная архитектура (из корневого `README.md`):

```
VK Parser → Kafka → AI Service (TagsAI) → ClickHouse/Analitic → Gateway → пользователь
                                   ↘ Postgres (карточки постов/комментариев) → VKParserServiceFastAPI
```

Проект — набор из **7 независимых сервисов** в монорепозитории, оркестрируемых через `docker-compose.yml` (Kafka, Zookeeper, Redis, 2×Postgres, ClickHouse, Kafka UI + сами сервисы).

## Что реально работает end-to-end

- Сбор данных из VK (Java-парсер) → публикация комментариев в Kafka — **работает**.
- Регистрация/логин пользователя через Gateway → UserService → Postgres — **работает**.
- Чтение комментариев из Postgres через Gateway → VKParserServiceFastAPI — **работает как API**, но без данных (см. ниже).

## Ключевые разрывы в пайплайне (почему это не "готовый продукт")

1. **Нет моста между VK-парсером и Postgres-сервисом.** VKParser пишет в Kafka/JSONL-файлы, а VKParserServiceFastAPI читает из отдельной Postgres-базы — нет процесса, который бы наполнял эту базу (нет consumer'а Kafka → Postgres).
2. **TagsAI не задеплоен.** Нет Dockerfile, нет сервиса в `docker-compose.yml`, нет модели в репозитории — AI-анализ комментариев нельзя запустить "из коробки".
3. **ClickHouse ничем не наполняется.** Analitic ожидает таблицу `messages` с полями `sentiment`, `region`, `topics` и т.д., но ни TagsAI, ни другой сервис туда не пишут — источник этих полей (sentiment/region) в принципе больше нигде в коде не определён.
4. **`infrastructure/db/create_db.sql` — это пустая директория, а не SQL-файл.** Docker при монтировании несуществующего файла как volume создал на его месте каталог, поэтому инициализация БД `vkservice_db` не выполняется.
5. **Опечатка в `docker-compose.yml`**: build-контекст `./VKParserServiceFastApi` (с маленькой `a`) не совпадает с реальным именем папки `VKParserServiceFastAPI` — на Linux (регистрозависимая ФС, как в большинстве Docker-образов) сборка этого сервиса упадёт.
6. **Фронтенда/UI нет.** README ссылается на `http://localhost:8081`, но в репозитории нет ни одной директории с фронтендом.
7. **Аутентификация в Gateway не проверяется** — эндпоинты просто проксируют запросы, нет middleware для проверки JWT перед обращением к защищённым ресурсам.

## Рекомендации по приоритету (что делать дальше)

1. Исправить опечатку в `docker-compose.yml` и превратить `infrastructure/db/create_db.sql` в настоящий SQL-файл со схемой.
2. Написать consumer, который читает результаты TagsAI из Kafka и пишет их в ClickHouse (`messages`) и/или в Postgres — это единственное недостающее звено, чтобы дашборд ожил.
3. Задеплоить TagsAI: добавить Dockerfile, сервис в compose, решить вопрос с весами модели (обучить и закоммитить/захостить отдельно, т.к. веса добавлять в git не стоит).
4. Определиться с судьбой `VKParserServise` (Spring Boot) — удалить как дубликат либо доосознанно вести параллельно.
5. Добавить проверку JWT на Gateway и/или в защищённых сервисах, реализовать смену пароля в UserService.
6. Спроектировать и реализовать фронтенд/дашборд — сейчас есть только backend API без UI.
