## Отчёт о ходе работ. Этап 1: исследование источников и состава данных

## 1. Тема и задачи проекта

Проект посвящён анализу жалоб жителей города, которые публикуются в городских и районных пабликах ВКонтакте: проблемы ЖКХ, дорог, вывоза мусора, транспорта и т. п. Жители часто сообщают о проблемах в соцсетях раньше, чем через официальные каналы, поэтому такие данные позволяют быстрее увидеть, где и когда возникают проблемы.

Аналитические задачи проекта:

1. Динамика и распределение жалоб по категориям (ЖКХ, дороги, мусор, транспорт) во времени: часы, дни недели, сезоны.
2. Сравнение профиля проблем и активности жителей между районами города.
3. Классификация тональности и тематики сообщений методами NLP и машинного обучения.
4. Кластеризация текстов и тематическое моделирование (Topic Modeling) для поиска скрытых групп локальных проблем.
5. Прогнозирование резонансности жалобы по первичным признакам публикации.
6. Графовый анализ обсуждений в комментариях и поиск лидеров мнений.
7. Проверка статистической гипотезы о различии характера обращений в будни и выходные.

## 2. Текущий этап

На первом этапе команда:

- определила, какие данные нужны для каждой из задач;
- изучила VK API и выбрала методы, которые дают эти данные;
- разработала тестовый сборщик данных `VKCollector`;
- выбрала три городских паблика Санкт-Петербурга и собрала по ним пробную выборку за одну неделю;
- проверила, что собранные данные содержат все поля, необходимые для решения задач.

## 4. Инструмент сбора данных

Для изучения данных разработан тестовый сборщик **VKCollector** (Java 17, Maven). Он обращается к VK API и сохраняет посты и комментарии выбранных пабликов в файлы формата JSONL (одна запись — одна строка JSON). Сборщик сделан намеренно простым — без очередей сообщений и баз данных, — чтобы быстро проверить, какие данные доступны, и в дальнейшем использовать его как основу модуля сбора.

Возможности:

- сбор постов за заданный период (`--since`, `--until`);
- сбор комментариев к каждому посту, включая полные ветки ответов и отметки «Нравится»;
- ограничение частоты запросов к API и повторные попытки при временных ошибках;
- пропуск недоступных пабликов и отдельных ошибочных запросов без остановки всего сбора.

Используемые методы VK API:

| Метод | Что даёт |
|---|---|
| `groups.getById` | сведения о паблике: название, число подписчиков, город |
| `wall.get` | посты: текст, дата, отметки «Нравится», репосты, просмотры, число комментариев |
| `wall.getComments` | комментарии: текст, дата, автор (числовой ID), отметки «Нравится», ветки ответов |

Пример запуска:

```
java -jar vk-collector.jar --groups spb_2026,spb_today,o_st.petersburg --since 2026-09-28 --until 2026-10-04
```

## 5. Состав данных и их применение в задачах

| Данные | Поля | Для каких задач |
|---|---|---|
| Текст поста и комментариев | `text` | 3, 4 — классификация тональности и тематики, кластеризация, тематическое моделирование; 1 — разметка по категориям |
| Время публикации | `date` (с точностью до секунды) | 1 — динамика по часам, дням недели и сезонам; 7 — гипотеза «будни / выходные» |
| Реакция аудитории | `likes`, `reposts`, `views`, `comments.count` | 5 — целевая переменная и признаки для прогноза резонансности |
| Структура обсуждения | `from_id`, `thread`, `parents_stack`, `reply_to_user` | 6 — граф «кто кому отвечает», поиск лидеров мнений |
| Источник | паблик, число подписчиков | 2 — сравнение сообществ и районов; нормировка активности на размер аудитории |

Персональные данные (имена, контакты, профили авторов) не собираются: автор комментария представлен только числовым идентификатором, которого достаточно для построения графа обсуждений. В отчётах и презентациях используются только агрегированные данные.

## 7. Выводы и следующие шаги

**Выводы этапа 1:**

- VK API предоставляет все данные, необходимые для решения поставленных задач: тексты, точное время публикации, показатели реакции аудитории и структуру обсуждений.
- Тестовый сборщик работает и позволяет выгружать данные за произвольный период.
- **Паблики сильно различаются по содержанию.** Почти все обсуждения (98 % комментариев) приходятся на spb_today — паблик о происшествиях, куда в том числе пишут сами жители (10 из 124 постов за неделю прислали читатели). o_st.petersburg публикует преимущественно афишу и материалы о городе, spb_2026 — коммерческие объявления без комментариев. Жалобы жителей составляют лишь часть потока, поэтому на следующем этапе список источников будет расширен пабликами, ориентированными на жалобы, и районными сообществами.
- **Простой поиск по ключевым словам не подходит для разметки.** Словарь категорий («дорога», «мусор», «автобус», «двор» и т. п.) отметил 69 постов из 192, но жалобами из них являются единицы: слова встречаются в криминальных новостях, анонсах музеев и рекламе. Это подтверждает необходимость классификации тематики методами NLP и машинного обучения (задача 3).
- **В выходные постов публикуется примерно в 2,5 раза меньше**, чем в будни. При проверке гипотезы о различии обращений в будни и выходные (задача 7) нужно сравнивать доли и характер сообщений, а не их абсолютное число.
- **Данных для графового анализа достаточно**: только в одном паблике за неделю — 1 904 уникальных автора комментариев, ветки обсуждений достигают 65 ответов.

**Риски:**

- **Объём данных.** Для набора требуемого объёма (не менее 2 ГБ) потребуется расширить список пабликов и период сбора: активный паблик уровня spb_today даёт около 4,4 МБ сырых данных в неделю, т. е. порядка 115 МБ за полгода, — для 2 ГБ нужно 15–20 таких пабликов за 6 месяцев. Скорость сбора ограничена лимитами частоты запросов VK API (неделя по трём пабликам собирается примерно за 1,5 минуты).
- **Районная привязка.** В данных VK нет поля «район», поэтому для сравнения районов (задача 2) в выборку нужно добавить районные паблики, в которых район определяется самим сообществом.
- **Закрытые сообщества.** Часть пабликов может быть закрыта или ограничивать комментарии — список источников проверяется перед сбором.

**Следующие шаги.** С учётом рекомендаций по упрощению стека сначала будет построена минимальная рабочая версия системы: ETL-процесс на Python, запускаемый по расписанию (cron), загружает данные сборщика в ClickHouse, а анализ и визуализация выполняются на Python (pandas). На этой основе будут решаться аналитические задачи — разметка жалоб по категориям, статистический анализ и NLP-модели. После этого система будет развиваться в сторону полноценной архитектуры: потоковая передача данных через Kafka, распределённая обработка на PySpark и веб-интерфейс на FastAPI и React. Сборщик данных остаётся на Java и будет расширен под новые источники.
