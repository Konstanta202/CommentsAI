# Вариант 1: Городская аналитика по жалобам в соцсетях

## Предметная область

Мониторинг и аналитика общественных жалоб/проблем, которые жители городов публикуют в гиперлокальных пабликах ВКонтакте («Подслушано [город]», районные и соседские паблики). В отличие от анализа официальных новостных комментариев, здесь люди сами формулируют проблему своими словами — более «сырой» и информативный текстовый материал для NLP.

Категория по классификации методички: **Social Mining** (анализ соцсетей) + элементы **Text Mining**.

## Практическая ценность

- Городские службы и администрация узнают о проблемах (ямы на дорогах, мусор, шум, проблемы ЖКХ) быстрее, чем через официальные обращения — люди жалуются в соцсетях раньше, чем пишут в госуслуги.
- Можно обнаружить кластеры повторяющихся жалоб по районам/темам — приоритизация, куда направить ресурсы в первую очередь.
- Демонстрирует прикладную ценность Data Science «для общественного блага» — сильный аргумент на защите.

## Что и как собираем

**Источники**: 3-5 пабликов «Подслушано [город]» / районных сообществ из разных городов (для межрегионального сравнения). Пример подбора: 1 паблик крупного города-миллионника + 1-2 паблика городов поменьше + 1 паблик отдельного района/микрорайона.

**Поля**:
- Посты: id, дата, текст, лайки/репосты/просмотры, число комментариев, тип вложений (без скачивания медиа)
- Комментарии: id, from_id (псевдоним VK, не ФИО), дата, текст, лайки, thread (ответы), parents_stack, post_id

**Объём**: пабліки типа «Подслушано» обычно очень активны (десятки постов в день, сотни комментариев) — должно быть проще всего добрать до 2 ГБ из всех вариантов.

**Период**: 6-12 месяцев истории через `run`-режим с `--since`, затем `--watch` для актуализации к защите.

**Важный нюанс**: from_id — это числовой VK ID, не персональные данные в чистом виде, но при публикации в отчёте/презентации не стоит деанонимизировать конкретных авторов жалоб (152-ФЗ, элементарная этика) — использовать только агрегаты.

## Архитектура

```
VK Parser (Java) → Kafka → Ingestion/Cleaning (Python)
                                    ↓
                              MongoDB (сырое хранилище, обязательная NoSQL)
                                    ↓
                    Обработка (pandas/sklearn + PySpark + LLM API)
                                    ↓
                         ClickHouse (аналитическая витрина)
                                    ↓
                    Gateway (FastAPI, JWT) → React-дашборд + Grafana
```

Архитектура не зависит от выбранного домена — меняется только список групп для парсера и схема категорий в NLP-классификации.

## Распределение ролей и задач (20 задач)

### Джавист — временная и инфраструктурная динамика
1. Динамика количества жалоб по дням недели и часам суток — когда люди жалуются активнее *(статистическая)*
2. Время до первой реакции сообщества (комментарий/лайк) на новую жалобу *(статистическая)*
3. Кластеризация районов/городов по профилю активности во времени, K-means *(исследовательская)*
4. Прогноз, наберёт ли жалоба много откликов, по признакам первых минут *(исследовательская, регрессия)*
5. Оценка потерь данных из-за rate-limit VK API — полнота выборки по группам *(статистическая)*

### Fullstack #1 — AI/RAG/LLM-аналитика содержания
1. Классификация жалоб по категориям через LLM API (ЖКХ/дороги/мусор/шум/безопасность/другое) без дообучения *(исследовательская)*
2. Тональность обсуждений жалоб *(статистическая)*
3. Тематическое моделирование (эмбеддинги) — динамика проблемных тем во времени *(исследовательская)*
4. RAG-бот: «какие проблемы чаще всего обсуждают в районе X за последний месяц» — семантический поиск + суммаризация *(исследовательская)*
5. Сравнение LLM-классификации категорий с лексикон-baseline на контрольной выборке *(исследовательская)*

### Fullstack #2 — сетевой анализ и тяжёлая обработка
1. Граф «кто кому отвечает» в обсуждениях + выявление активных локальных лидеров мнений *(исследовательская)*
2. Детект накрутки/скоординированных вбросов (фейковые жалобы, боты) *(исследовательская)*
3. Кросс-групповой анализ авторов — одни и те же жалобщики в разных районных пабликах *(исследовательская)*
4. PySpark: построение агрегированной «карты проблем» на всём корпусе (частоты категорий по районам) *(исследовательская, закрывает критерий Hadoop-экосистемы)*
5. Доля жалоб без реакции vs «резонансных» — распределение вовлечённости *(статистическая)*

### Аналитик — описательная статистика
1. Распределение длины жалобы и корреляция с лайками/комментариями (Пирсон/Спирмен) *(статистическая)*
2. Динамика числа жалоб по неделям/месяцам — тренд и сезонность *(статистическая)*
3. Сравнение активности между районами/городами, топ-N самых обсуждаемых проблем *(статистическая)*
4. Сводная статистика по категориям жалоб (на основе вывода Fullstack #1) *(статистическая)*
5. Проверка гипотезы: значимо ли отличается число жалоб в будни vs выходные (t-test/хи-квадрат) *(исследовательская)*

## Риски и особенности

- Нужно явно исключить/анонимизировать персональные данные в отчёте и презентации.
- Паблики «Подслушано» бывают закрытыми для парсинга через модерацию — проверить доступность API до финального выбора конкретных групп.

## Соответствие критериям методички

| Критерий | Как выполнено |
|---|---|
| Объём данных ≥2ГБ | Высокая активность пабликов, `run`-режим за 6-12 мес |
| 5-20 задач, статистика+исследование | 20 задач, оба типа представлены у каждого участника |
| NoSQL БД | MongoDB как сырое документ-хранилище |
| Экосистема Hadoop/Spark | PySpark-задача у Fullstack #2 |
| Продвинутые методы | LLM-классификация, эмбеддинги, RAG, community detection, anomaly detection |
